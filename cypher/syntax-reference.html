Cypher Patterns — Things You Can Do With This Data

Your own reference. All queries run against the fraud dataset (Person, Account, Transaction, Merchant, Device). Same shapes work on any other graph — just swap the labels.

Before anything else — the two kinds of "names" you'll see everywhere below:
  • Nicknames like p or a right after MATCH — think of it like putting a name tag on whatever you just found, so you can point at it again later in the same query. That's it. Nothing fancier.
  • AS something after RETURN — this just renames the column heading in your results table, like retitling a spreadsheet column so it reads nicely. It does nothing else. Delete it and the query still works, the column just shows an uglier default name.
Favorites file ready to import: cypher/favorites-fraud.csv — everything below, plus a verify-count query. Setup (constraints, loading the CSVs) isn't in there — that's already done and documented in the README. Import via Neo4j Browser's Favorites panel.
1

List everything

MATCH (p:Person)
RETURN p.name AS person, p.risk_score AS risk_score;
  • MATCH (p:Person) — find every node labeled Person, call it p.
  • RETURN x AS y — pick which properties to show, and rename the column.
Result: 8 rows — Alice 85, Bob 78, Carol 92, Dave 65, Eve 88, Frank 72, Grace 80, Hannah 20.
2

Sort it

MATCH (p:Person)
RETURN p.name AS person, p.risk_score AS risk_score
ORDER BY p.risk_score ASC;
  • ORDER BY goes after RETURN, sorts the rows.
  • Default is ASC (smallest/oldest/lowest first) if you omit it — write DESC to flip it.
Result: Hannah 20, Dave 65, Frank 72, Bob 78, Grace 80, Alice 85, Eve 88, Carol 92.
3

Filter by a condition

MATCH (t:Transaction)
WHERE t.amount > 500
RETURN t.transaction_id AS transaction, t.amount AS amount;
  • WHERE comes after the MATCH it filters, before RETURN.
  • Operators: > < >= <= = <> (<> = "not equal").
Result: 6 transactions — T003 (900), T004 (875), T005 (850), T006 (600), T007 (550), T010 (1200).
4

Count everything (one total number)

MATCH (p:Person)
RETURN count(p) AS total_people;
  • count(p) is an aggregating function — it collapses all matched rows into one.
  • Because nothing else un-aggregated is in RETURN, you get a single row back, not one per person.
Result: 8.
5

Look up one specific thing's connections

MATCH (p:Person {name: "Alice Martin"})-[:OWNS]->(a:Account)
RETURN a.account_id AS account;
  • {name: "..."} — inline filter, only match the node with this exact property value.
  • -[:OWNS]-> — follow only relationships of type OWNS, in the direction the arrow points.
Result: A100 and A101.
6

List every pair (no filter, all matches)

MATCH (p:Person)-[:OWNS]->(a:Account)
RETURN p.name AS person, a.account_id AS account;
  • Same shape as #5, just drop the {name: ...} — now it returns one row per person-account pair that exists, not just one person's.
Result: 9 rows — Alice Martin appears twice (A100, A101), everyone else once.
7

Follow a relationship backwards

MATCH (a:Account {account_id: "A300"})<-[:OWNS]-(p:Person)
RETURN p.name AS owner;
  • <-[:OWNS]- — arrow points into the node on the left instead of out of it. Same relationship type, opposite direction of travel.
  • Use this when you start from the "target" (the account) and want the "source" (its owner).
Result: Carol Singh.
8

Count per group (implicit GROUP BY)

MATCH (p:Person)-[:OWNS]->(a:Account)
RETURN p.name AS person, count(a) AS account_count;
  • Cypher has no GROUP BY keyword. Whatever's in RETURN that isn't wrapped in an aggregating function (here, p.name) automatically becomes the grouping key.
  • One row per distinct person; count(a) only counts that person's accounts.
Result: Alice Martin → 2, everyone else → 1.
9

Filter on a relationship's own property

MATCH (a:Account)-[paid:PAID]->(m:Merchant)
WHERE paid.amount > 100
RETURN a.account_id AS account, m.name AS merchant, paid.amount AS amount;
  • [paid:PAID] — giving the relationship itself a variable name lets you read its properties, not just the nodes on either end.
  • Relationships can hold data too (amount, date, channel) — not just nodes.
Result: A700 → Fast Electronics ($1200), A300 → Crypto Voucher Store ($400).
10

Only the top one

MATCH (p:Person)
RETURN p.name AS person, p.risk_score AS risk_score
ORDER BY risk_score DESC
LIMIT 1;
  • LIMIT 1 keeps only the first row left after sorting — sort first, then cut.
Result: Carol Singh, 92.
11

Top N

MATCH (p:Person)
RETURN p.name AS person, p.risk_score AS risk_score
ORDER BY risk_score DESC
LIMIT 3;
  • Same as #10, just change the number. LIMIT always comes last.
Result: Carol Singh (92), Eve Carter (88), Alice Martin (85).
12

Total per group

MATCH (a:Account)-[:SENT]->(t:Transaction)
RETURN a.account_id AS account, sum(t.amount) AS total_sent
ORDER BY total_sent DESC;
  • Exact same implicit-grouping trick as #8, just sum() instead of count().
Result: A700 (1750), A300 (1300), A400 (875), A500 (850), A600 (600), A100 (250), A200 (245.5), A800 (45), A101 (30).
13

Total per group, using a relationship's own property

MATCH (a:Account)-[paid:PAID]->(m:Merchant)
RETURN m.name AS merchant, sum(paid.amount) AS total_paid
ORDER BY total_paid DESC;
  • Combines #9 (reading a relationship's own property, paid.amount) with #8/#12's implicit-grouping trick — m.name isn't aggregated, so it's the group key, same as always.
  • The only difference from #12: the thing being summed lives on the relationship (paid.amount), not on the node at the end of it (t.amount). Whenever the value you need to total is stored on the arrow itself rather than a node, this is the shape you reach for.
Result: Fast Electronics (1200), Crypto Voucher Store (400), Campus Cafe (65.5).
CRUD — everything so far only reads. These four write. Use a throwaway test node (not real data) so you can demo Create/Update/Delete without messing up the other patterns above.
14

Create a node

CREATE (p:Person {person_id: "P999", name: "Test Person", risk_score: 50})
RETURN p;
  • CREATE — unlike MATCH, this doesn't search for anything, it just makes a brand-new node with these properties, every time it runs.
  • Run this twice and you get two separate "Test Person" nodes — CREATE never checks if one already exists.
Result: a new Person node, P999 / Test Person / risk_score 50.
15

Create a relationship

MATCH (p:Person {person_id: "P999"})
CREATE (a:Account {account_id: "A999", account_type: "checking", status: "active"})
CREATE (p)-[:OWNS]->(a)
RETURN p.name AS owner, a.account_id AS account;
  • First line finds the existing person from #14 with a normal MATCH.
  • Second line creates a new Account node.
  • Third line creates the OWNS arrow connecting them — you can CREATE a relationship between any two nodes you already have in hand.
Result: Test Person → owns → A999.
16

Update a property

MATCH (p:Person {person_id: "P999"})
SET p.risk_score = 95
RETURN p.name AS name, p.risk_score AS risk_score;
  • MATCH first to find the node you want to change — SET only works on something you already matched.
  • SET p.risk_score = 95 overwrites that one property. Everything else on the node stays untouched.
Result: Test Person, risk_score now 95.
17

Delete (cleanup)

MATCH (p:Person {person_id: "P999"})
OPTIONAL MATCH (p)-[:OWNS]->(a:Account {account_id: "A999"})
DETACH DELETE p, a;
  • OPTIONAL MATCH — like MATCH but doesn't fail the whole query if nothing matches (in case the account was already gone).
  • DETACH DELETE — deletes the node and any relationships attached to it in one go. Plain DELETE on a node with relationships still attached throws an error; DETACH is what lets you skip finding and deleting each relationship by hand.
Result: Test Person and its account are gone — verified 0 nodes left over.
